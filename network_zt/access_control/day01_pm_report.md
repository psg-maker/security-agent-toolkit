## 6교시 · 권한 판정 함수 `check_permission`

### 문제 6-1 · 권한 판정 함수 `check_permission` 직접 쓰기

- (가) 채우기 전에 실행한 출력 아홉 줄과, 내가 채운 코드를 붙여 넣어 주세요.

  - 답: 채우기 전에는 [1] 사용자 등록 여부만 검사하므로 minsu만 거부되었다.

채운 코드(함수 안에서 앞 공백 4칸을 더해 사용):

```python
if not USERS[user]["employed"]:
    return False, "퇴사한 계정"
role = USERS[user]["role"]
if role not in ROLES:
    return False, "역할이 없음"
permission = f"{resource}:{action}"
if permission not in ROLES[role]:
    return False, "권한 없음"
```

  - 쓸 내용: 자유롭게
  - 답: 사용자 등록 여부만 검사하면 퇴사자나 권한 없는 사용자도 통과할 수 있으며, 먼저 실패한 검사에서 반환한 이유가 최종 거부 사유로 남는다는 것을 알게 되었다.

## 7교시 · 접속 기록 다시 판정하기 · 쓰이지 않는 권한 찾기 · 올리기

### 문제 7-1 · 접속 기록을 다시 판정하며 쓰이지 않는 권한 찾기

- (가) 🔍 실행한 출력에서 허용 · 거부가 각각 몇 건이고 거부된 번호가 무엇인지 적고, 10/19(월) 의 점수 판단(PDP)은 낮의 12 · 14 ~ 17번을 막지 못했는데 RBAC 는 막은 이유를 두 방식이 무엇을 보고 판정하는지 비교해 설명해 주세요.
  - 쓸 내용: ① 허용 · 거부 건수와 거부된 번호 ② 점수 판단이 보는 것 ③ RBAC 가 보는 것 ④ 왜 달라졌는지
  - 답: 허용 7건, 거부 8건이며 거부된 번호는 3·4·5·12·14·15·16·17번이다. 점수 판단은 기기·시각·국가·조회 건수 같은 접속 상황을 평가하므로, 등록 기기에서 낮에 적은 건수로 조회한 12·14~17번은 위험 점수가 낮아 허용되었다. RBAC는 역할에 해당 자원과 행위의 권한이 있는지 확인한다. sales에는 SETTLE:QUERY가 없으므로 상황이 정상처럼 보여도 정산 조회 8건을 모두 거부한다. 두 방식은 보는 기준이 달라 함께 적용할 필요가 있다.

실제 실행 출력:

```text

[거부] 4 02:15 seoyeon SETTLE QUERY - 권한 없음

[거부] 12 13:40 seoyeon SETTLE QUERY - 권한 없음
[거부] 14 14:10 seoyeon SETTLE QUERY - 권한 없음
[거부] 15 14:35 seoyeon SETTLE QUERY - 권한 없음
[거부] 16 15:00 seoyeon SETTLE QUERY - 권한 없음
[거부] 17 15:25 seoyeon SETTLE QUERY - 권한 없음
허용 7 거부 8
{'batch-night 허용': 1, 'seoyeon 거부': 8, 'junho 허용': 3, 'seoyeon 허용': 3}
쓰이지 않음 sales SALES:CHANGE
쓰이지 않음 account_admin ACCOUNT:QUERY
쓰이지 않음 account_admin ACCOUNT:CHANGE
쓰이지 않음 finance SALES:QUERY
쓰이지 않음 auditor SALES:QUERY
쓰이지 않음 auditor SETTLE:QUERY
```

- (나) 🔍 이 결과만으로 「RBAC 를 켜면 정상 업무는 막히지 않는다」고 말할 수 있나요? 이 기록으로 확인되는 것, 확인되지 않는 것, 기록이 하루치뿐이라서 생기는 한계를 적어 주세요.
