# 3과목 총정리 (이름 · 2026-11-02(월))

## 상황 1 · 새 직원이 들어옴 (본보기)
- 원인: 데이터 문제입니다. hana 가 입사했는데 `users.json` 에 hana 가 아직 없습니다. 시스템은 사용자 파일에 없는 사람의 요청을 모두 「등록되지 않은 사용자」로 거부합니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: 새로 넣습니다. hana 를 `"hana": {"role": "sales", "employed": true}` 로 `users.json` 에 적습니다. `role` 은 hana 가 맡을 일에 맞는 역할로 정합니다.
- 고친 뒤 확인: hana 의 요청을 다시 판정해서 「등록되지 않은 사용자」가 사라지는지 봅니다.

## 상황 2 · 퇴사자 계정으로 요청이 계속 들어옴 (본보기)
- 원인: 데이터가 정리되지 않았습니다. dami 는 퇴사했는데 dami 의 항목이 `users.json` 에 그대로 남아 있어서 같은 시도가 계속 들어옵니다. `employed` 가 `false` 이면 요청은 거부되지만, 남은 항목 때문에 퇴사자 계정 점검에는 계속 걸립니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: dami 의 `"employed"` 가 `true` 로 남아 있다면 먼저 `false` 로 바꿉니다. 이미 `false` 이면 그대로 두고, dami 의 항목 전체를 `users.json` 에서 지웁니다.
- 고친 뒤 확인: 같은 요청이 「등록되지 않은 사용자」로 거부되고, 퇴사자 계정 점검이 통과로 바뀌는지 봅니다.
- 더 써 보고 싶은 것(선택): `check_permission` 이 퇴사 여부를 역할 확인보다 먼저 보는 이유는 무엇일까요?

## 상황 3 · 다른 팀 업무를 잠시 지원함
- 원인: 기존 역할에는 다른 팀의 업무 권한이 없어 임시 지원 요청이 거부되는 상황임.
- 고칠 파일: `config/exceptions.json`
- 어떻게 고치나요: 승인된 사용자·권한·만료 시각·사유를 예외로 추가함. 잠깐 필요한 권한이므로 기존 역할 전체를 바꾸지 않음. 지원이 끝나면 남은 예외를 정리함.
- 고친 뒤 확인: 다른 조건도 충족한 요청이 만료 전에는 예외로 허용되고, 만료 시각부터는 거부되는지 확인함.
- 더 써 보고 싶은 것(선택): 영구적인 업무 변경이면 예외를 계속 연장하기보다 역할 변경을 검토해야 함.

## 상황 4 · 새 권한이 필요함
- 원인: 권한을 요청하고 승인·부여하는 절차가 없으면 담당자가 임의로 권한을 주거나 승인 기록이 누락될 수 있음.
- 고칠 파일: `req_create.py`, `req_review.py`, `req_grant.py`
- 어떻게 고치나요: 요청서를 만들고 다른 담당자가 검토한 뒤, 승인된 요청만 예외 권한으로 부여하도록 처리함. 요청자가 자신의 요청을 승인하지 못하게 함.
- 고친 뒤 확인: 요청 상태가 `reviewing` → `approved` → `granted`로 바뀌고, 본인 승인과 미승인 요청의 부여는 차단되는지 확인함.
- 더 써 보고 싶은 것(선택): `req_sla.py`로 처리 기한을 넘긴 요청도 찾아 담당자가 확인하도록 함.

## 상황 5 · 안 쓰는 권한이 쌓임
- 원인: 부여한 권한을 정기적으로 확인하지 않아 사용하지 않는 권한이 계속 남는 상황임.
- 고칠 파일: `review_unused.py`, `report_exclude.py`, `config/access_log.json`, `config/exclude_list.json`
- 어떻게 고치나요: 사용 이력이 없거나 마지막 사용 후 90일을 넘긴 권한을 회수 후보로 찾음. 계절 업무 등 계속 필요한 권한은 사유를 기록하여 제외하고, 퇴사자 권한은 제외 목록에 있어도 회수 대상으로 둠.
- 고친 뒤 확인: 91일 미사용 권한은 후보에 포함되고 정확히 90일인 권한은 빠지는지 확인함. 필요한 권한과 퇴사자 권한이 각각 회수 제외와 회수 대상으로 구분되는지도 확인함.
- 더 써 보고 싶은 것(선택): 미사용은 회수 후보를 찾는 기준임. 실제 업무 필요성을 확인한 뒤 회수해야 함.

## 상황 6 · 민감한 권한을 회수해야 함
- 원인: 불필요한 권한이 남아 있으나 쓰기 권한이나 여러 권한을 한 번에 회수하면 정상 업무에도 영향을 줄 수 있음.
- 고칠 파일: 회수 대상에 따라 `config/exceptions.json`, `config/users.json`, `config/roles.json`임. 승인·이력 처리는 교재의 회수 절차를 참고함.
- 어떻게 고치나요: 회수할 권한과 영향받는 사용자를 먼저 확인함. 민감한 권한이거나 영향이 큰 회수는 책임자 승인 후 실행하고, 승인되지 않은 계획은 대기 상태로 둠. 실행 여부와 사유를 이력으로 남김.
- 고친 뒤 확인: 승인 전에는 권한이 유지되고 승인 후에는 해당 권한만 제거되는지 확인함. 회수 전후 판정과 이력도 비교함. 이미 거부되던 요청은 회수 후에도 거부될 수 있음.
- 더 써 보고 싶은 것(선택): 역할의 권한을 제거하면 같은 역할을 가진 모든 사용자에게 적용되므로 영향 범위를 확인해야 함.

## 상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨
- 원인: 시간·접속 위치 조건이 빠지면 위험한 요청이 허용될 수 있고, 조건이 실제 업무와 맞지 않으면 정상 직원도 거부될 수 있음.
- 고칠 파일: 교재의 `config/conditions.json`임. 현재 작업 폴더에는 이 파일이 없어 적용 시 별도 구성이 필요함.
- 어떻게 고치나요: 교재 예시에서는 `SALES:CHANGE`를 9시 이상 18시 미만, 사내망 또는 VPN에서만 허용함. gaeun의 VPN 업무가 승인된 정상 업무라면 `ACCOUNT:CHANGE`의 허용 위치에 VPN을 추가하고 외부 접속은 계속 제한함.
- 고친 뒤 확인: 업무 시간의 정상 VPN 요청은 허용되고, 외부 접속이나 업무 시간 밖 요청은 거부되는지 확인함. `[9, 18]` 조건에서 18시 정각이 거부되는지도 확인함.
- 더 써 보고 싶은 것(선택): 거부를 줄이려고 조건을 무조건 풀면 위험한 요청도 허용될 수 있으므로 과거 로그로 영향을 비교해야 함.

## 상황 8 · 매주 어긋남을 확인해야 함
- 원인: 사람이 매주 계정·예외·로그를 직접 확인하면 누락이 생기고 같은 기준으로 비교하기 어려움.
- 고칠 파일: `checklist.py`, `log_summary.py`, `weekly_report.py`, `config/week_state.json`, `config/alert.json`
- 어떻게 고치나요: 퇴사자·만료 예외·부서와 역할 불일치를 점검하고, 로그의 허용·거부 수와 사유를 집계하여 주간 보고서로 만듦. 경고 기준을 조정할 때는 변경 이유도 기록함.
- 고친 뒤 확인: 현재 예시에서는 요청 40건 중 허용 24건·거부 16건, 거부율 40%로 기준 30% 이상 경고가 나옴. 거부 4번 이상 사용자는 dami와 gaeun이며, 점검에서는 dami의 퇴사 계정과 junho의 부서·역할 불일치가 나오는지 확인함.
- 더 써 보고 싶은 것(선택): 빈 로그의 거부율 0%를 안전하다는 뜻으로 읽으면 안 됨. 전체 요청 수와 서버·로그 수집 상태를 함께 확인해야 함.
